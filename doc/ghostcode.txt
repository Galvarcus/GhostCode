Ghostcode is an analyzer for unreferenced code in Vim9 script, with Vim plugin
functionality. It scans a project for functions, methods, classes, fields,
enum values, and script-level variables, then reports every one that nothing
in the project ever calls or reads.

The analyzer is a command line program. The Vim plugin runs it and puts the
findings in the quickfix list.

The plugin looks for the binary at `g:ghostcode_bin`, then on `$PATH`, then in
a `bin/` directory of its own. Create that directory and put a release asset
in it, named `ghostcode`, or `ghostcode.exe` on Windows, to keep the binary
beside the plugin. When the plugin finds no binary, it says so through Logger
and names each place it looked.

==============================================================================
Usage                                                          *ghostcode-usage*

------------------------------------------------------------------------------
In Vim                                                        *ghostcode-in-vim*

Ghostcode adds one command:

                                                                  *:GhostCode*
>vim
    :GhostCode [path]
<
`path` is the root of the project to scan. It defaults to the working
directory of Vim.

It puts the findings in the quickfix list, opens the list when it finds any,
and shows a summary through Logger:

>text
    Ghostcode - ghostcode.vim - Report: 23 symbols, 7 ghost
<
Each entry names the kind of symbol, its name, its file, and its line:

>text
    autoload/util.vim|16 col 1| [ghost] function TrulyDeadFunction
    autoload/util.vim|37 col 1| [ghost] method DeadMethod
    autoload/util.vim|58 col 1| [ghost] variable g_never_read
<
Logger reads its options for Ghostcode from variables named
`g:logger_ghostcode_<option>`. See the Logger README for each option.

==============================================================================
Settings                                                    *ghostcode-settings*

------------------------------------------------------------------------------
`ghostcode.toml`                                      *ghostcode-ghostcode.toml*

A project states its own settings in `ghostcode.toml`, in its root:

>toml
    # Whether an exported symbol is public API, so that nothing reports it.
    exports_are_api = false

    # Paths to leave out, beyond the ones git ignores.
    ignore = ["deps/**", "vendor/**"]

    # Files that are entry points, whose top-level code needs no caller.
    entry = ["tools/build.vim"]

    # Scoped variables written for a reader outside the project.
    external = ["g:tlinks_*"]

    # The finding classes to report beyond the default.
    [findings]
    locals = true
    globals = true
    buffer_vars = true
    window_vars = true
    tab_vars = true
<
`exports_are_api` is true by default. Ghostcode then treats an exported symbol
as public API and never reports it. Vim9 cannot export a method or a field by
itself, so every method and field of an exported class counts as exported too,
unless its name starts with an underscore. A global function, `def g:Name`,
counts as exported, because any user or plugin can call it.

Set it to false for a plugin whose exports serve only its own files, as in an
application. Ghostcode then reports an export that nothing in the project
uses, like any other symbol.

`findings.locals` is false by default. Set it to true to report a `var` or a
`const` of a function body that nothing in that body reads. An assignment is
not a read, so a local the code only writes is reported too. A parameter and a
`for` variable are left alone.

The finding reads `[local]` rather than `[ghost]`, so a build that counts the
ghosts counts none of these.

`findings.globals`, `findings.buffer_vars`, `findings.window_vars`, and
`findings.tab_vars` are false by default. Each one reports the variables of
one scope, `g:`, `b:`, `w:`, or `t:`, that the project writes and nothing
reads:

>text
    plugin/example.vim:12:1:[ghost] variable g:example_width
<
These rules decide what counts as a read:

- `g:name` in code, and `g:name` inside any string.
- `get()` and `has_key()` on a scope, `exists()`, and the `getbufvar()`
  family. `setbufvar()` and its kin are writes.
- A name held in a `const` of the same file whose value is one string.
- A name built at run time, as `get(g:, $'example_{kind}_width')`, which reads
  every variable that its fixed parts fit.

These do not count as a read:

- A second write.
- A read in the command that writes the variable. The `get()` of
  `g:name = get(g:, 'name', default)` reads what the user set, so a setting
  that no other line reads is reported.
- A read in code that nothing reaches.

The finding names the write that takes the user's value where one exists, and
otherwise the first write by path and line. Ghostcode reports no variable that
the Vim help documents, such as `b:current_syntax`.

The finding reads `[ghost]`, so a build that counts the ghosts enforces it
once the flag is on.

A line that uses a scope with no fixed name, such as `keys(g:)` or
`get(g:, name)`, reads every variable of that scope. Ghostcode then reports
none for the scope and says so on stderr, with the file and the line:

>text
    ghostcode: autoload/example.vim:35: every g: variable counts as read from this line, so none is reported
<
In Vim the same message goes to the log and not to the quickfix list.

`external` lists the scoped variables that the project writes for another
plugin to read. Give the full spelling. A `*` stands for any run of
characters. Ghostcode never reports a variable listed there.

==============================================================================
What Ghostcode scans                            *ghostcode-what-ghostcode-scans*

Ghostcode reads the files git does not ignore, whether git tracks them or not.
Outside a repository nothing is ignored and every file is read. It stops at
the project root and follows no symlink out of it, because a finding outside
the root is one you cannot act on. It skips hidden directories, as Vim's own
`globpath` does; name a file in `entry` to scan one anyway.

==============================================================================
What Ghostcode detects                        *ghostcode-what-ghostcode-detects*

- `def` and `export def`
- `class` and `export class`, including `extends` and `implements`
- `enum` and `export enum`, and enum values (`Color.Red`)
- `interface` and `export interface` declarations
- class methods, static methods, and fields
- module-level script variables and class fields
- a `var` or a `const` of a function body that nothing in that body reads,
  where you ask for the class, see Settings
- type annotations (`var x: Foo`, `def F(): Foo`, `list<Foo>`)
- direct calls (`Foo()`), method calls (`Foo.Bar()`, `this.Method()`), and
  calls through a locally-typed variable or parameter, including a two-level
  field-then-method chain on `this` (`this.field.Method()`)
- a method called directly on a constructor result (`Foo.new(args).Bar()`)
- bare funcref and value usage of a known symbol (`var Ref = Foo`,
  `timer_start(1000, Foo)`, `{callback: Foo}`)
- names inside string interpolation (`$'see {LABEL} here'`)
- `call()`, `function()`, `execute()`, and `exists()`, where the target is a
  string literal or bare identifier
- a name that any other string holds, where the project declares a symbol of
  that name, because Vim evaluates text in places a parser cannot see: the
  right-hand side of a mapping, a `feedkeys` sequence, a substitution opening
  with `\=`
- every `import` form: relative paths, `import autoload`, and named imports
  (`import {Foo} from '...'`)
- exported symbols, treated as public API and never reported as dead unless
  you turn that off, see Settings
- the classic `plugin#Function()` autoload calling convention
- top-level code in scripts that Vim sources directly (`plugin/`, `ftplugin/`,
  `ftdetect/`, `syntax/`, `indent/`, `compiler/`, `colors/`, `keymap/`,
  `lang/`, and their `after/` copies) and in `tests/` or `test/`, all treated
  as entry points that need no call site

==============================================================================
What Ghostcode doesn't detect           *ghostcode-what-ghostcode-doesnt-detect*

- a parameter or a `for` variable that nothing reads. Only a `var` or a
  `const` of a function body is reported, and only where you ask for the
  class: a parameter is part of a signature that a caller outside the project
  may hold to
- dynamic dispatch built from string concatenation, computed indices, or
  anything else that isn't a literal identifier or string
- method calls on a variable with no declared or inferable type. When a
  variable's type can't be determined, Ghostcode falls back to the class
  members of that name across the project. When several classes declare the
  name, it counts every one of them as used. A name behind a dot never counts
  as a use of a function or a variable of that name
- calls into a file outside the project root. An import that names another
  plugin, or a copy of one under a directory such as `deps/`, is not followed,
  so nothing in that file is counted as used through it
- a script variable or a field that the code only writes and never reads. A
  write counts as a use there. Inside a function body it does not, so a local
  the code only assigns to is reported with the other locals
- a legacy `function` that nothing calls. Only a `def` is a symbol. A call
  from the body of a legacy function still counts as a use

Ghostcode is conservative by design: anything it can't prove is unreferenced
is left alone rather than reported.
